# BF16 sparse SDPA K64 vs K32 A/B — 2026-08-14

## Summary

The BF16 sparse SDPA qtile256 path was tested with the selected-block K tile changed from 64 tokens
to 32 tokens, matching the dense `ark.sdpa` head_dim=128 K tile size. This is an experimental patch,
not yet a cleaned-up final implementation.

Result: **K32 is substantially faster**. At topk 0.5, BF16 sparse changes from slower than dense
`ark.sdpa` to clearly faster.

## Test setup

- Branch: `feat/sparse-bf16-prefill-v2`
- Device: Intel Battlemage XPU, `ZE_AFFINITY_MASK=5`
- Benchmark: `benchmarks/bench_sparse_topk.py`
- Shape: `seq_len=75000`, HND, 40 heads, head_dim 128
- Sparse config: `q_tile_override=256`, `sparse_q_block_tokens=256`, `sparse_k_block_tokens=64`
- Benchmark options: `--warmup 1 --iters 2`
- Baseline CSV: `benchmarks/results/ab_k64_bf16_20260814_090508.csv`
- K32 CSV: `benchmarks/results/ab_bf16_sdpa_k32_20260814_092404.csv`

## Patch shape

The A/B changed `launch_sparse_sdpa_prefill_kernel_128` in
`auto_round_kernel/wrapper/include/sycl_tla_sdpa_sparse.hpp`:

```cpp
// K64 original
using ShapeQK = Shape<_256, _64, _32>;
using ShapePV = Shape<_256, _32, _64>;

// K32 experiment
using ShapeQK = Shape<_256, _32, _32>;
using ShapePV = Shape<_256, _32, _32>;
```

Because the routing LUT still uses 64-token sparse K blocks, the experiment also changed
`auto_round_kernel/wrapper/include/stla/xe_sparse_sdpa_fwd_mainloop.hpp` so each sparse route block
can expand into multiple physical K microtiles. For the K32 experiment, one 64-token routed block
runs as two 32-token mainloop iterations.

## Tile meaning

For QK:

```cpp
using ShapeQK = Shape<_256, _32, _32>;
```

This means:

```text
M = 256   query tokens per workgroup tile
N = 32    key tokens per physical K microtile
K = 32    head-dim reduction chunk
```

The QK output score tile is therefore `256 x 32`. Since head_dim is 128, each physical tile still
does four reduction chunks over the feature dimension:

```text
head_dim 128 / reduction chunk 32 = 4 QK reduction chunks
```

For PV:

```cpp
using ShapePV = Shape<_256, _32, _32>;
```

This means:

```text
M = 256   query rows / probability rows
N = 32    value/output head-dim columns per tile
K = 32    selected key/value tokens reduced per PV tile
```

So one PV microtile consumes `P[256, 32] x V[32, 32] -> O[256, 32]`. The output head_dim 128 is
covered as four 32-column output chunks.

Pseudocode for one selected 64-token sparse route block:

```cpp
// K64 original:
// ShapeQK = Shape<_256, _64, _32>
// ShapePV = Shape<_256, _32, _64>
for each selected_route_block_64_tokens {
    scores[256][64] = 0;
    for d = 0; d < 128; d += 32 {
        scores[256][64] += Q[256][d:d+32] * transpose(K[64][d:d+32]);
    }
    softmax_update(scores[256][64]);
    O[256][0:32] += P[256][64] * V[64][0:32];  // repeated for output-dim chunks
}

// K32 experiment:
// ShapeQK = Shape<_256, _32, _32>
// ShapePV = Shape<_256, _32, _32>
for each selected_route_block_64_tokens {
    for micro_tile = 0; micro_tile < 2; ++micro_tile {
        key_start = selected_route_block_64_tokens * 64 + micro_tile * 32;

        scores[256][32] = 0;
        for d = 0; d < 128; d += 32 {
            scores[256][32] += Q[256][d:d+32] * transpose(K[key_start:key_start+32][d:d+32]);
        }
        softmax_update(scores[256][32]);
        O[256][0:32] += P[256][32] * V[key_start:key_start+32][0:32];  // repeated for output-dim chunks
    }
}
```

The head-dim reduction loop count is the same in both cases (`128 / 32 = 4`). The difference is the
physical selected-key span:

```text
K64: one route block -> one 256x64 score tile
K32: one route block -> two 256x32 score tiles
```

K32 adds one extra microtile iteration per 64-token route block, but each physical tile is smaller.
The unitrace result below shows that smaller tile wins because it greatly reduces SEND/SBID and
memory-write pressure.

## Interpretation

This confirms the K64 selected-block microtile is a major performance issue for BF16 sparse SDPA.
The kernel properties pass shows that K64 does cause compiler-reported spill memory:
`Spill Memory Per Thread` is **3840 B** for K64 and **0 B** for K32. SLM remains 0 because this is
private/scratch spill traffic, not SLM-backed storage.

The runtime metrics match that diagnosis. K64 is memory/SEND scoreboard limited: SBID stall rises
from 31.4% to 55.7%, XVE active drops from 64.7% to 39.9%, SEND instructions rise 4.4x, and memory
writes rise ~5.0x. The large LSC write delta is now best interpreted as spill/scratch pressure plus
the extra memory traffic created by the larger K64 live state.

Recommendation: keep the selected-block BF16 sparse SDPA path on K32 and treat K64 as a regression
case unless compiler/offline assembly data proves the write/SBID pressure can be removed another way.
